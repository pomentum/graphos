Whitepaper · version 2026-10-05

pomentum/graphos

graphos

A graph store many services can share without sharing a database. PostgreSQL and Apache AGE underneath, a typed HTTP API on top.

This paper explains the problem graphos addresses, the decisions behind it, how it works and what it gives the people who build on it and run it. Numbers are marked measured only where they come from a benchmark or a profiled query; everything else is a property of the design.

In 30 seconds

  • The problemConnected data turns up in most systems. Once several services need it, each one ends up holding database credentials, its own Cypher, and its own answers to bulk loading, indexing and isolation.
  • The approachOne service owns the graph. Consumers call a typed REST API; graphos alone talks to PostgreSQL + Apache AGE on a private network.
  • What you getA graph per tenant, tokens scoped to tenants and to read or write, COPY-speed idempotent writes, in-place edits of single nodes and edges guarded by revisions, composable reads including shortest paths and a map of the whole graph, a change feed to follow every write, optional Louvain communities with stable ids, rule-based edges, background jobs for long operations, a web UI for people, and ordinary Postgres operations.
  • What it is notNot a general query console, not a new database engine, and not tied to any domain: graphos ships no labels of its own.
  • LicenceApache 2.0, like the Apache AGE extension it is built on.

01The problem

Graphs are rarely the product, but they are often underneath it: links between documents, people and the teams they belong to, ownership and access relationships, lineage, recommendations. Storing them is the easy part. The difficulty starts when more than one service needs the same graph store.

The usual pattern is that each service adds a database driver, a connection string, and its own query text. That works for one consumer. With several, the same costs appear every time:

  • Credentials spread. Every consumer holds a database login, so every consumer can run any query, against any data.
  • Query text is copied and drifts. The same traversal is written slightly differently in each service, with different limits and different bugs.
  • There is no tenant boundary. Separating one team's or one dataset's graph from another becomes a convention in application code rather than something the system enforces.
  • One slow query affects everyone. An unbounded variable-length match can hold connections and I/O that every other consumer is waiting for.
  • Everyone re-solves bulk loading. Row-by-row MERGE is the obvious way to write a graph and also the slowest; each team discovers that separately.
  • Analytics happen off to the side. Community detection is exported, computed elsewhere and written back, and the community ids change on every run, which breaks anything that remembered them.
  • Operations need a specialist. A dedicated graph database is one more product to back up, monitor, upgrade and secure.

02The approach

graphos rests on four decisions. Each one removes a class of the problems above rather than mitigating it.

Postgres, not a new engine
The graph lives in PostgreSQL through the Apache AGE extension. You keep MVCC, disk-backed storage, pg_dump, streaming replication and pg_stat_statements, and still query with openCypher.
The boundary is HTTP
Consumers speak typed JSON. The queries are written inside graphos, once, as SQL over AGE's tables, with checked identifiers and capped limits. No connection string leaves the service.
A tenant is a graph
Each tenant gets its own AGE graph. A token lists the tenants it may touch and whether it may write; the tenant is in the URL and is checked before any SQL runs.
The schema is the consumer's
graphos ships no labels and interprets no properties. Consumers declare labels at registration; every endpoint takes label, property and edge names as parameters.

graphos owns the data plane and generic graph operations. The meaning of the data stays with whoever wrote it.

03How it works

graphos is two containers. graphos-db is PostgreSQL 16 with Apache AGE and has no externally reachable port. graphos-api is a FastAPI service on asyncpg and is the only thing that can reach it. Consumers join a separate network and call the API with a bearer token.

Tenants and registration

A consumer registers a tenant by posting its vertex labels, edge labels and, optionally, extra indexes and generated columns. graphos creates the AGE graph, the per-label tables and a unique index on each label's external id. Registration is idempotent and additive, so a consumer can simply re-register on every start; it is persisted, so a restart of graphos needs nothing from consumers. Writing to an unregistered label returns 400; the schema never grows silently.

Writing

PathUse it forBehaviour
Small upsertsUp to ~1,000 rows per callUpsert on your id; property updates are additive

Snapshot importOne file holding a whole graphNodes and edges in one stream, nodes flushed before edges
One node or edgeAn editor changing one itemJSON Merge Patch of its properties; an edge is read, patched or deleted by its type and end ids; If-Match refuses a stale edit

All three write through the same path: a binary COPY into a staging table, then one INSERT … ON CONFLICT per label. graphos writes no rows through Cypher. That is faster, and it also avoids an AGE 1.6 crash: a Cypher write into a label table that carries extra columns (graphos adds one to edge tables; generated columns add more) takes down the database backend. Edges whose endpoints do not exist yet are counted in edges_skipped rather than failing the batch, so ordering mistakes are visible without losing work. Nodes can be deleted by id or by a property predicate, for example everything belonging to one dataset; each delete removes the nodes and every edge touching them in one statement, so they go together or not at all.

To change one item in place, a PATCH applies a JSON Merge Patch to one node or one edge: null removes a key, nested objects merge, everything else replaces. The row is read, locked, patched and written back in one transaction. Ids are unique within a label but not across labels, so an id can name nodes in two labels; a call that would match more than one row is refused with the candidate labels (409) and changes nothing, rather than landing on an arbitrary row or on all of them.

Every node and edge carries a revision that every write bumps, and a single node or edge is returned with an ETag made of its internal id and that revision. Sending it back as If-Match makes the write conditional: if anyone else has written the row since it was read, the answer is 412 with the current ETag and nothing changes, so two editors never silently overwrite each other. The check runs on the locked row inside the write's transaction, and a deployment can make If-Match mandatory for these writes.

Reading

Reads are small primitives that compose: ranked search, one-hop neighbors, multi-seed expand up to five hops, the shortest paths between two nodes, the induced subgraph of a node set, a paginated node scan with filters and projection, a stratified sample for visualisation, histograms, top-K by degree, node and edge aggregates, and an export in graphology JSON that sigma.js and Gephi read directly.

For a first look at a large graph there is a graph map: every label with its node count, and every pair of labels with the number of edges of each type between them. It reads AGE's storage directly: an edge's ends carry their labels in their internal ids, so no vertex table is joined. Very large edge tables are sampled and their counts marked as estimates, which keeps the map to about a second on ten million edges; an exact count is one parameter away. The map also names each label's best-connected nodes, the natural place to start exploring it.

Shortest paths are found by searching from both ends at once, one batched SQL statement per level over the edge indexes, always growing the smaller side; every path of the shortest length is returned, up to a limit. A level that would touch more than 100,000 edges stops the search and says so, rather than wandering through a hub. AGE's own shortestPath is not used.

Search runs through search indexes a tenant declares at registration, as with the full-text indexes of other graph databases: a name, the labels it covers (or all of them, including labels added later), the properties it searches, and an analyzer. The identifier analyzer reads names, identifiers and paths as words, with camelCase, acronyms and punctuation split, so getUserById is found by get user by id, getuserbyid or GetUserByID. Hits rank exact, then prefix, then contained, then similar words, which also catch most typos; misspellings can be asked for on top. The text analyzer is Postgres full-text search, with stemming and phrase, or and exclusion syntax, for prose. Every hit carries a score and the property it matched. The indexes are ordinary Postgres GIN indexes, updated in the same transaction as the write, so a node is findable the moment it is committed. Without a search index, search is a substring match on name, or on any other property named in the call.

Following changes

Every write is also recorded in a change feed, in the same transaction, so a record exists exactly when the data committed and a write that rolls back leaves none. A record says what changed (the ids written, the new revision of a single item, who wrote it), not the new values. Consumers keep a cursor and read what changed after it, or follow the feed live as Server-Sent Events, resuming with Last-Event-ID after a dropped connection; a commit wakes the stream at once. To sync from scratch: take the feed's head, read the data, follow from the head. A cache, a search index or an open editor stays current by applying only what changed, instead of rescanning the graph or polling it.

The feed never skips a committed change, even when transactions commit in a different order from the one they started in: a record becomes visible once every write that started before it has finished. Records are kept for seven days by default; a consumer that falls further behind is told to resync (410) rather than silently missing changes.

Looking at it

graphos also ships an optional web UI, an nginx image with no backend of its own: it forwards to the API on the same origin, and each person signs in with their own token, so a read-only token gets a read-only UI and every edit is recorded under its author. A large graph opens on its map, or on its communities; a small one on its whole graph. On the canvas, neighbours arrive a page at a time beside the node they belong to, the view follows them, and every step can be undone. Nodes and relationships are edited with the same revision checks as the API: a node changed by someone else meanwhile is flagged, not overwritten. Shortest paths, a table view of a label, live activity and the schema (which administrators can extend) complete it. It reads the tenant's shape from the API, so a new label appears without a UI change.

Safety rails

  • Read endpoints cap their limit parameters and report truncated when a result was cut.
  • Every statement runs under a server-side statement_timeout (60 s by default); one that runs too long is cancelled by Postgres and the request returns 504 as problem+json instead of holding the pool. The few deliberately long operations (index builds, Louvain, rule resolution, vacuum) raise the limit for their own statements only, and Louvain, rule resolution and vacuum can also run as background jobs (section 6). Every endpoint is plain SQL, never Cypher: on a large graph, AGE's Cypher executor was seen ignoring both the timeout and a cancel for over ten minutes.
  • Label and property names are checked against an identifier pattern and the tenant's registered schema, and index or generated-column DDL supplied at registration must be a single CREATE INDEX / ADD COLUMN … GENERATED statement on the tenant's own tables, so neither can carry arbitrary SQL.
  • Authentication fails closed: without a tokens file graphos will not start unless local-only anonymous mode is switched on explicitly.
  • Tokens can be read-only. Every operation declares whether it reads or writes, and the OpenAPI schema shows it; a test fails if an operation declares neither, if any tenant operation accepts another tenant's token, or if any write accepts a read-only one. A dashboard or a viewer can hold a token that cannot change anything.
  • graphos-api connects to Postgres as an unprivileged role (no superuser, cannot create roles or databases); the superuser is only used to initialise the database.
  • Endpoints that need no token (health, readiness, service info) report counts, never tenant names or database error text.

04Communities that stay put

Clustering a graph into communities is useful for navigation, for summarising large graphs and for narrowing a traversal to the relevant neighbourhood. graphos runs Louvain itself, close to the data, with one admin call.

Optional extra. Louvain uses python-igraph, which is GPL-licensed, so it is not part of the default install or the published image. Add it with pip install "graphos[louvain]" or --build-arg GRAPHOS_EXTRAS=louvain; without it the endpoint answers 501 and everything else works. GET /v1/info reports whether it is present.

The step that matters most is the matching. Louvain on its own numbers clusters arbitrarily, so a re-run gives every community a new id even when almost nothing changed. graphos compares each new cluster with the previous partition and keeps the old id when the overlap is high enough (the method of Greene et al., 2010). Ids are stable on stable input and drift gracefully on changing input, so dashboards, caches and saved filters keep working. The partition itself depends only on the graph: vertices are numbered by id before clustering, so the same edges give the same communities however their rows happen to be stored.

After the write-back, each edge carries the community of its endpoint in an indexed column, so a traversal scoped to a few communities is an index lookup rather than a recursive walk. Runs are single-flight per tenant, can be scoped to a subgraph by property, and can be weighted per relationship type. The clustering runs in its own process, so the API keeps answering other requests meanwhile; a long recompute can run as a background job, and cancelling it stops the computation and frees its memory.

Each recompute also leaves a community map. It already holds every edge it clustered, so one more pass gives each community's size, its members per label, its best-connected member and the edges between communities per relationship type, exactly and at no extra read. The map is stored with the result and served instantly at any graph size: a picture of how a large graph divides and connects, with each community named after its hub rather than its number.

05Edges from rules

Many edges are implied by properties: a document lists the tag keys it carries, and each tag node has its own key. The usual way to materialise them is to page every node out, match in application code and write the edges back. graphos lets a consumer declare the rule once, at registration:

{ "name": "TAGGED", "resolve_rule": { "src_has_array": "tag_keys", "dst_value_from": "concat(collection, '/', slug)", "require_dst_label": ["Tag"], "require_same": ["team"] } }

A call to edges:resolve compiles each rule into one parameterised INSERT … SELECT … JOIN and runs it inside the database. The rule language is a closed set of nine keys, so it cannot carry SQL, and graphos creates the supporting indexes itself. Re-running is idempotent.

06Operating it

graphos is meant to be run by a platform team that knows nothing about any tenant's data.

  • Health: /healthz, /readyz and /v1/info with service and AGE versions.
  • Metrics: Prometheus request counts and latency histograms per route and status, connection-pool size, registered tenants, and rate-limit rejections.
  • Logs and audit: structured JSON logs carrying a W3C traceparent trace id; every write (an operation declared as a write, whatever its HTTP method, including one refused for its token) also produces an audit record with tenant, calling consumer, status, latency and a hash of the request body.
  • Database introspection for admins: table and index sizes, dead tuples, slow queries from pg_stat_statements, and a validated vacuum call.
  • Change feed: records are pruned after the retention period in short transactions; on shutdown, open streams are closed after a few seconds so a stop never hangs, and their clients resume on another replica.
  • Background jobs: community recompute, rule resolution and vacuum accept Prefer: respond-async and answer 202 at once with a job to poll at /v1/jobs/{id}. A finished job holds exactly what the synchronous call returns; each job runs once, on any replica, and can be cancelled, which stops the work rather than just the wait.
  • Several replicas: any number of API replicas can share one database behind a load balancer. A tenant registered or changed through one is picked up by the others at once (Postgres LISTEN / NOTIFY), and so are K/V cache writes; a replica that missed a notification looks an unknown tenant up before answering and re-reads every registration every 30 seconds, so nothing depends on the notification arriving. Jobs run once across replicas, and change streams resume on any of them.
  • Tokens reload on SIGHUP, so rotation needs no restart (signal every replica). An optional per-token rate limiter protects shared deployments; each replica limits on its own.
  • Web UI: an optional nginx image next to the API, opted into with one compose profile; it needs no database access, no secrets of its own and no CORS set-up.
  • Everything else is Postgres: backups, replicas, upgrades and tuning use the tools your team already runs.

09Boundaries and limits

Some choices are deliberate in the current design:

  • Typed endpoints rather than query passthrough. graphos does not expose a raw Cypher or SQL endpoint today; that is what keeps limits, timeouts and tenant checks enforceable. Pattern queries are composed from primitives (scan for a node set, then neighbors or induced edges), and new needs are met by adding typed endpoints.
  • No connection strings for consumers, and no DDL through the API beyond tenant registration.
  • No domain concepts. Labels and properties are opaque strings to graphos.

And some limits that are simply where the project stands today:

  • The reference deployment is a single PostgreSQL node. It fits millions of nodes and tens of millions of edges in a few gigabytes of RAM. Going beyond one node (partitioning, read replicas) is a PostgreSQL exercise; graphos does not shard for you.
  • A change-feed record becomes visible once every write transaction that started before it has finished, on the whole database server. That is usually milliseconds, but a long write (a Louvain write-back on a large graph) holds every tenant's feed until it commits; nothing is lost.
  • Louvain is an optional extra (see section 4). When installed, each recompute builds its graph in memory in a child process of the API: the API holds about 20 bytes per edge while streaming them, the child holds the graph, and the memory is released when the run ends. One recompute runs at a time per API process; the bundled compose file gives the API 2 GB.
  • The graph map samples very large edge tables, so its counts there are estimates and a label pair with only a handful of edges inside such a table can be missing; an exact count reads everything. The community map is as current as the last recompute.
  • Search ranks by kind of match and closeness, not by BM25 as Lucene-based engines do: strong for names and identifiers, basic for long prose, with no highlighting. It ranks a bounded set of candidates per label, so a query of one very common word may miss the best hit; more words or a label narrow it.
  • Apache AGE 1.6 has known Cypher gaps and quirks. graphos works around the ones it meets, and the AGE notes record each one.

10Built on Apache AGE

graphos uses Apache AGE, the PostgreSQL extension that adds a property-graph model and openCypher queries to Postgres. The bundled stack runs the upstream image apache/age:release_PG16_1.6.0 unmodified.

AGE provides the graph engine: each graph is a Postgres schema, each label is a table inheriting from a parent vertex or edge table, properties are stored as agtype, and Cypher runs inside the database through the cypher() function. Because it is plain Postgres underneath, graphos can use SQL where it is faster and better behaved, and it does so for every endpoint: bulk writes through COPY, functional and trigram indexes on properties, set-based edge derivation, and reads that statement timeouts and cancellation always apply to.

graphos adds what a shared service needs on top: the HTTP contract, tenancy and tokens, bulk paths, index management, community detection, rule-based edges and observability.
